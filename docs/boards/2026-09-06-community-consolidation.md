# Starlight Board — community contracts and branch consolidation

Source: Codex task `01a0740d-878e-7dc1-88c5-86f91ec18382`; SIS issues #66 and #123.

**Sovereign:** I require retained source branches and explicit distinctions between source integration, deployment, and publication. The user's consolidation request authorizes reviewed merges, not new external sends or commerce.

**Seer:** I challenge coupling the shared community model to a platform. Keep external adapters in consuming repositories and reject unsupported versions and capabilities explicitly.

**Harmonizer:** I require member consent to come from the authenticated host, never an inbound event's self-declaration. Public and durable projections must exclude raw messages and private matching rationale.

**Strategist:** I support the existing #66 creation-cell loop as the smallest useful expansion. A portable workflow package and deterministic event reducer let community operators prove a week before buying infrastructure.

**Verifier:** I require replay/collision, tenancy, consent, lifecycle, and privacy tests. Passing source tests cannot establish a connected host, staffed support, marketplace publication, or production readiness.

**Overseer:** The load-bearing concern is accidental promotion of unfinished or differently owned work through bulk merges. Proceed with explicitly reviewed source contracts, preserve blocked work, and obtain independent review plus CI before merging the integration branch.

**Recommendation:** PROCEED for additive source integration and fixture-level community implementation, conditional on independent review and passing checks. External authority changes and unverified production surfaces remain excluded.

**Rationale:** This advances the already accepted operating model without changing SIP semantics or surrendering member sovereignty.
