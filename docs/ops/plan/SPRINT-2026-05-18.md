## Public changelog best practice (recommendation)

Three surfaces, ranked by leverage:

1. **GitHub Releases** (highest leverage, lowest effort) — Industry-standard tag-based release notes. Auto-discoverable via `github.com/frankxai/Starlight-Intelligence-System/releases`. Use `gh release create <tag> --notes-file <slice-of-CHANGELOG.md>`. RSS feed comes free at `<repo-url>/releases.atom`.
2. **Site `/changelog` route** (medium leverage, low effort) — Next.js page at `starlightintelligence.org/changelog` rendering CHANGELOG.md via existing `lib/markdown` pipeline. Adds brand surface; readers don't need a GitHub account.
3. **CHANGELOG.md at repo root** (already done, source of truth) — Keep-a-Changelog format. The other two surfaces render from this.

**Anti-patterns to avoid:**
- Linear / Notion changelog (lives in SaaS, can't be forked by adopters)
- Twitter-only changelog (no version history, drifts immediately)
- Site changelog WITHOUT source CHANGELOG.md (divergence inevitable)

**Industry references for format:** [keepachangelog.com](https://keepachangelog.com), [Vercel changelog](https://vercel.com/changelog), [Anthropic changelog](https://docs.anthropic.com/en/release-notes/api). All three follow the same shape: dated entries, version-tagged, semantic-versioned, headline-then-bullets.
