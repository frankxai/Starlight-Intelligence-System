# First value through repeat and export

| Stage | User action | Success | Failure/recovery |
| --- | --- | --- | --- |
| Admit | Select an existing repository, outcome, permitted paths, placement and budget. | A server-issued scoped mission and reservation exist before work starts. | Missing identity, grants, balance or residency yields a precise unavailable/denied state. |
| Connect | Enroll one approved local node and inspect its declared capabilities. | Fresh authenticated evidence identifies the node and allowable tasks. | Offline, revoked and stale capability reports are visible; no work is sent. |
| Start | Start a bounded change from the laptop. | A tenant/resource lease and generation bind the active attempt; progress and source revision are inspectable. | Retry the same operation identifier only with its unchanged payload. |
| Handoff | Checkpoint work, disconnect the original executor and resume on an approved target. | A new generation is admitted; the target verifies source and checkpoint digests before starting. | Wait for lease expiry or explicit release. Reject old-owner renewal, completion and artifact promotion. |
| Review | Inspect the PR, evidence and proposed release from desktop or phone. | Keyboard/mobile review references the exact artifact hash and head revision. | Changed output invalidates approval. Loading, disconnected and partial states remain distinct. |
| Accept and settle | Accept a useful result or request one bounded revision. | One idempotent settlement records actual supplier usage and releases unused allowance. | Reconcile late usage and uncertain effects; cancellation does not erase incurred cost. |
| Repeat and export | Reuse the proven playbook or export the work to another runtime. | Repository source, context manifest, event history and artifact references reopen with original provenance. | Corrupt, missing or unauthorized bytes are rejected. Commercial upgrade stays a hypothesis until repeat use is demonstrated. |
