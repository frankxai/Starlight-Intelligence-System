This doctrine turns the plugin estate into a public-facing product system, not just an internal tool collection.

## Core Idea

The public idea is simple:

> Starlight Intelligence Modules are installable capabilities for building, proving, and distributing better work.

Use these layers:

| Layer | Public framing | Internal meaning |
| --- | --- | --- |
| Ecosystem | FrankX AI, Starlight Intelligence, Arcanea | The full business and creative estate |
| Product line | Founder Command, Revenue Engine, Arcanea World Engine | A coherent business outcome |
| Plugin | Intelligence Module | Installable capability bundle |
| Skill | Method | Specific agent behavior inside a module |
| Workflow | Playbook | Repeatable first-run or business process |
| Bundle | Kit or Suite | Curated set of modules with docs and release artifacts |

This creates a clean story: founders buy outcomes, builders install modules, agents execute methods.

## Founder Appeal

Founders and ambitious operators do not want "plugin ops." They want clarity, leverage, speed, proof, and distribution. Naming should make those benefits obvious before anyone reads the documentation.

Use founder-attractive names that answer one of these questions:

| Founder question | Naming pattern | Examples |
| --- | --- | --- |
| What should I build next? | Command, Graph, Registry | FrankX Command, Ecosystem Graph, Domain Registry |
| How do I make money from this? | Engine, Architecture, Marketplace | Checkout Engine, Offer Architecture, Agent Marketplace |
| How do I make this look excellent? | Studio, Visual Intelligence, Motion | Motion Design Studio, Visual Intelligence |
| How do I protect the upside? | Shield, Veil, Guard | IP Shield, Private Memory Veil, Publication Guard |
| How do I prove quality? | Lab, Evals, Proof | Prompt Evaluation Lab, Starlight Evals Lab |
| How do I distribute it? | Release, Download, Publisher | Release Sites, Template Publisher, Download Pages |

Good names should be:

- Outcome-led: name the result, not the internal mechanism.
- Short: two or three words when possible.
- Boardroom-readable: credible in a founder, investor, or enterprise conversation.
- Demo-friendly: easy to say in a walkthrough.
- Searchable: distinctive enough to find in docs, registries, and releases.
- Expandable: broad enough to hold multiple skills without becoming vague.

Avoid names that sound like internal chores unless the buyer is truly buying operations. `Ops` is acceptable only when operations is the product promise, such as `Agentic Ops Harness`.

## Brand Boundaries

The estate needs separation by language, emotional promise, and publication surface.

| Brand lane | Job | Language to use | Language to avoid |
| --- | --- | --- | --- |
| Starlight Intelligence | Intelligence infrastructure and system modules | intelligence, modules, graph, memory, evals, release, proof, command | magical, lore, myth, ritual, destiny |
| FrankX AI | Founder-facing business authority and offers | founder, revenue, command, offer, growth, consulting, execution, proof | lore-heavy Arcanea terms, private vault language |
| Arcanea | Magical worlds, living lore, worldbuilding, creator studios | worlds, canon, genesis, fabric, characters, mythic, studio, creator forge | enterprise CoE language, generic business jargon |
| Enterprise AI | Corporate trust, implementation, migration, governance | CoE, migration, governance, readiness, workshops, enablement, evidence | mystical language, playful fantasy framing |
| Creator and Media | Products, templates, audio, visual systems | studio, launch, drops, media kit, release, audience | regulated claims, overpromised income language |
| Health and Specialist | Sensitive guidance with clear boundaries | intelligence, protocol, reflection, safety, behavior loop | diagnosis, cure, guaranteed health outcomes |

The Arcanea leak test:

1. If a module is for enterprise, founders, revenue, checkout, or partner distribution, Arcanea terms are not allowed in the public name or default copy.
2. If a module is for magical worlds, lore, canon, characters, world repositories, or creator mythology, Arcanea should be explicit.
3. Cross-selling is allowed only as a bridge, not as mixed identity. Example: "Arcanea world packs can be distributed through Starlight release modules."
4. Private Arcanea canon, unreleased lore, private prompts, and premium studio process stay out of public starter bundles unless deliberately packaged.

## Plugin And Skill Naming

Plugin names and skill names have different jobs.

| Artifact | Job | Naming style | Example |
| --- | --- | --- | --- |
| Plugin display name | Public product appeal | Title Case, noun-led, outcome-led | Offer Architecture |
| Plugin slug | Install compatibility | kebab-case, stable, migration-protected | `pricing-packaging-ops` now, `offer-architecture` later |
| Skill name | Agent trigger clarity | short lowercase verb/noun phrase | `package-offer`, `tier-audit` |
| Workflow name | User journey | imperative or result-led phrase | Build a launch-ready offer ladder |
| Bundle name | Market package | audience plus outcome | Founder Command Kit |

Skill names should be plainer than plugin names. They are methods, not brands.

Examples:

| Plugin | Skill naming pattern |
| --- | --- |
| FrankX Command | `estate-brief`, `priority-map`, `founder-decision-log`, `execution-wave` |
| Offer Architecture | `price-ladder`, `package-offer`, `tier-audit`, `upgrade-path` |
| Checkout Engine | `checkout-audit`, `conversion-friction`, `payment-flow`, `cart-proof` |
| Ecosystem Graph | `repo-census`, `domain-map`, `plugin-coverage`, `risk-graph` |
| Starlight Memory | `memory-capture`, `context-rehydrate`, `evidence-save`, `privacy-check` |
| Arcanea Genesis | `world-seed`, `genesis-flow`, `coherence-gate`, `share-loop` |
| Arcanea Canon Director | `canon-review`, `character-bible`, `pillar-check`, `anti-trope-pass` |
| Motion Design Studio | `motion-brief`, `scroll-choreography`, `animation-qa`, `hero-motion-pass` |
| Publication Guard | `path-scan`, `claim-scan`, `license-check`, `private-boundary-review` |

Do not give skills grand names that compete with the plugin brand. A plugin is the product; a skill is the action.

## Distribution Architecture

Distribution should separate trust, conversion, and technical installation.

| Surface | Role | What belongs there |
| --- | --- | --- |
| GitHub Releases | Versioned source of truth | ZIPs, checksums, changelogs, install notes, source archives |
| `starlightintelligence.org/download` | Primary technical download home | Starlight modules, public starter bundles, machine-readable manifests |
| `frankx.ai/downloads` | Founder and business router | Outcome cards, demos, consulting paths, links to Starlight install pages |
| `arcanea.ai` or Arcanea surfaces | Creative and worldbuilding downloads | Arcanea starter worlds, world kits, creator packs, visual/media bundles |
| Private plugin marketplace | Internal operating system | Unsanitized modules, private strategy, premium IP, local-source workflows |

Recommended public flow:

1. A founder discovers the outcome on `frankx.ai`.
2. A technical user installs from `starlightintelligence.org/download`.
3. The release artifact and checksum live on GitHub Releases.
4. The first workflow produces a useful result in under ten minutes.
5. The upgrade path points to a kit, cohort, consulting offer, or full Starlight system.

Every public download needs:

- Version.
- Compatibility line.
- SHA-256 checksum.
- Install command.
- First workflow.
- Privacy and claim boundary.
- Changelog.
- Support or upgrade path.
- Link back to the brand/product line it belongs to.

## Release Ladder

Use a staged ladder instead of pushing everything public at once.

| Stage | Name | Contents | Public status |
| --- | --- | --- | --- |
| 0 | Private Suite | Full 45-plugin estate | Private only |
| 1 | Public Starter | Sanitized modules with low IP risk | Public prerelease |
| 2 | Founder Kit | Founder Command plus revenue and distribution workflows | Public or gated |
| 3 | Starlight System Module | Intelligence modules, evals, memory, release workflows | Public technical product |
| 4 | Arcanea World Kit | Arcanea Genesis, canon, world repo starter, media examples | Public creative product after IP review |
| 5 | Partner Suite | Licensing, partner portal, data room, media kit | Gated or partner-only |

The current private suite should remain private. Public releases should be rebuilt from sanitized source folders, not from the full private suite.

## Naming Rubric

Score every new plugin name from 1 to 5 before creating it.

| Criterion | Question |
| --- | --- |
| Clarity | Does a first-time user know what this is for? |
| Desire | Would a founder or creator want the outcome? |
| Domain fit | Does the name match the correct brand lane? |
| Distinctiveness | Is it memorable without being cute or confusing? |
| Expansion | Can it hold future skills without becoming bloated? |
| Public safety | Does it avoid private strategy, unreleased IP, and risky claims? |
| Migration cost | Can the slug be changed without breaking too much? |

Do not ship a new public-facing name below 28 out of 35 unless there is a strategic reason.

## What Else To Consider

Before broad distribution, decide these operational pieces:

| Area | Decision needed |
| --- | --- |
| License | Public starter license, commercial use rights, partner rights, Arcanea IP rights |
| Telemetry | Whether downloads, installs, and first-run workflows are tracked |
| Support | Where users ask for help, report issues, and request upgrades |
| Versioning | SemVer policy for plugins, skills, public bundles, and site manifests |
| Compatibility | Supported Codex versions, OS notes, plugin CLI requirements |
| Privacy | What data a workflow may read, store, publish, or summarize |
| Claims | Boundaries for income, health, legal, financial, and enterprise claims |
| Proof | Checksums, eval logs, screenshots, demo outputs, regression artifacts |
| Packaging | Public ZIPs, private suites, source repos, manifests, install commands |
| Showcase | Download pages, demo clips, screenshots, first workflow examples |

## Operating Cadence

Use this cadence to keep the system alive:

| Cadence | Action |
| --- | --- |
| Every plugin change | Validate source, validate installed cache, update changelog |
| Every public release | Run Publication Guard, rebuild sanitized bundle, publish checksum |
| Weekly | Review plugin usage, support friction, docs gaps, download analytics |
| Monthly | Re-score names, promote proven skills, retire weak candidates |
| Quarterly | Rebuild product-line bundles and refresh public positioning |

## Immediate Direction

The strongest next moves are:

1. Keep stable slugs for installed compatibility, but continue elevating public display names.
2. Reframe public plugins as Starlight Intelligence Modules.
3. Treat skills as methods inside modules, with plain action names.
4. Publish only sanitized public kits through GitHub Releases plus `starlightintelligence.org/download`.
5. Use `frankx.ai/downloads` as the founder-facing router, not the technical source of truth.
6. Keep Arcanea beautiful and explicit where it belongs, and absent from enterprise/founder modules unless the page is intentionally about Arcanea.
7. Build new plugins only when a skill cluster becomes a product line, a release surface, or a separate boundary.

This gives the portfolio the thing it needs most: names that sell the outcome, boundaries that protect the brands, and a distribution model that can scale without turning the system into a pile of clever labels.
