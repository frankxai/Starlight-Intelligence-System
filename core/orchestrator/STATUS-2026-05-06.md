## Current Gaps

- The SIS harness folders are load-bearing policy scaffolds, not yet an executable four-CLI wrapper.
- `starlight orchestrate` uses SIS orchestration abstractions. `starlight dispatch` now delegates to Arcanea's live CLI router, but it does not yet load per-harness prompt/MCP/tool policy into each target CLI.
- Arcanea `@arcanea/orchestrator` is the working dispatcher, but it has not been promoted under a Starlight package name.
- FrankX `.mcp.json` still has a broad `filesystem` MCP scoped to `.` and a Google Analytics placeholder credential path. Keep for utility, but treat as local-trust config, not community-default config.
- Broad SIS MCP propagation to every repo should be done repo-by-repo with smoke tests, not blindly.

## Action Plan

1. **Canonicalize naming:** keep package code in Arcanea for now, but document it as the Starlight dispatcher dependency.
2. **Harden the wrapper:** extend `starlight dispatch` so it loads the correct harness policy and can write outcome summaries into SIS memory after each run.
3. **MCP propagation batch:** add SIS MCP to Arcanea, ACOS, library-os, GenCreator, and Arcanea AI after each repo passes JSON/MCP smoke.
4. **Security posture:** convert broad/default MCP configs into trust profiles: local-owner, contributor-safe, and community-default. Community-default should not include broad filesystem, credentialed analytics, or write-capable memory by default.
5. **Self-learning loop:** route successful `arco` runs and SIS orchestrations into `.starlight` vaults with task, model, runtime, exit code, repo, and outcome notes. Adaptive routing should learn from this history, not from undocumented impressions.

## Practical Answer

This is not yet "top notch autonomous multi-CLI OS" end-to-end. It is now a strong foundation with verified memory/MCP, working CLIs, working cockpit layouts, and a tested dispatcher. The next high-value build is to connect those pieces into one operator command instead of adding another orchestrator repo.
