# Domain Stack Starter Template

> Drop-in scaffold for spawning a domain-specific intelligence sub-stack under SIP. Generated by `/spawn-domain-stack` or copied directly into `verticals/<vertical-slug>/` for manual fill. Generalizes the pattern proven by the People Intelligence sub-stack (renamed from HR Intelligence at v7.6.0) — every sovereign with a Genius Profile + Freedom Path + named domain expertise can spawn 4-7 functional sub-systems composing into a vertical.

## What's inside

| Path | What it declares | Fill-in required |
|------|------------------|------------------|
| `README.md` | This file — replace with your domain's overview | Your domain anchor + sub-system map |
| `SKILL.md` | Vertical-tier skill (loads when working in this vertical) | Voice, invariants, primary commands |
| `SOUL.md` | The essence that must not drift | Your single-sentence domain truth |
| `AGENTS.md` | Map SIP voice archetypes → your sub-system agents | One named sub-system agent per archetype slot (or vertical-specific declaration) |
| `MEMORY.md` | Instance state with sub-system roadmap section | Identity, sub-systems, commitments, fill order |
| `STACK.md` | Inheritance / override declarations | Stack choices |
| `PROPOSAL-template.md` | Architecture proposal output format | Filled by `/spawn-domain-stack` step 4 |
| `sub-system-template/` | Drop-in template for ONE sub-system | Copy per sub-system, populate |

## How a domain sub-stack differs from a regular vertical

A vertical (`/vertical-spawn`) is a single-domain intelligence system — one agent, one or two skills, a handful of commands. Good for thin domains where one functional area dominates.

A domain sub-stack (`/spawn-domain-stack`) is a multi-sub-system vertical — 4-7 sub-systems × (1 agent + 1 skill + 4-5 commands) each, composing under one vertical owner. Good for sovereigns whose lived domain expertise spans multiple functional areas that compose into one practice.

The trigger condition for a domain sub-stack:
- ≥10 years of lived practice in the domain, OR a credentialed multi-discipline synthesis edge.
- Named cross-domain synthesis edge (e.g., "psychology × neuroscience × MBA × HR-decade").
- ≥3 frameworks in your Genius Profile mappable to the domain.
- KEEP-bucket density ≥3 in this domain (Freedom Path).

If those are not met, use `/vertical-spawn` (lighter) or run `/discover-genius` first.

```
├── STACK.md                     — stack choices
├── CANON.md                     — canon adopt / decline

│
├── <sub-system-1>/              — one directory per sub-system
│   ├── agent.md                 — `starlight-<sub-system>` agent
│   ├── skill.md                 — `<domain-slug>/<sub-system>.md` skill
│   ├── knowledge.md             — research grounding template
│   └── commands/

│   └── ...
[repeat for 4-7 sub-systems]
```

## What you commit

- **File contract.** All vertical-tier files (SKILL, AGENTS, MEMORY, SOUL, STACK, CANON optional, README) + per-sub-system contracts.
- **Attestation.** Every shipped artifact carries "Built on SIP" via `/sip-attest`.
- **Sovereignty.** Your domain, your call. Starlight has no ownership claim.
- **Tier declaration.** Every sub-system agent declares "Domain Sub-Stack Tier" in its frontmatter (matches `starlight-hiring.md` precedent — these are sub-systems within your vertical, not universal layers).

## What you do NOT commit

- Private state in this repo (use `private/` gitignored directory).
- Any promise of ownership share with Starlight.
- Sub-systems that lack a synthesis-edge claim (commodity content belongs in `/creator-pipeline`, not in a domain sub-stack).
- Topical decomposition (chapters of a book, areas of expertise). Sub-systems must be functional — each command produces a named artifact.

## Customization rules

1. **Sub-system count: 4 ≤ n ≤ 7.** Bounded by the architecture skill (`integration/domain-stack-architecture`).
2. **Each sub-system: 4-5 commands.** Above splits; below merges.
3. **Synthesis edge appears load-bearing in ≥3 sub-systems.** Otherwise, the stack is a feature.
4. **Cross-sub-system composition declared.** Each sub-system's `agent.md` lists which sister sub-systems it composes with and how.
5. **Vertical SOUL.md filled before first sub-system fill.** The drift anchor anchors the entire stack — author it deeply.
