# Benchmarking Protocol

How to test memory substrates against the user's real corpus, without leaking private data.

## Why benchmark

Substrates are not interchangeable. Mempalace might beat Qdrant on recall@5 for episodic queries but lose on cold-tier latency. Letta might be the only option for self-editing memory. The right mix per user depends on:

- Corpus size + growth rate
- Query patterns (recall vs reasoning vs ambient)
- Privacy posture (cloud-okay vs sovereign)
- Hardware (CPU only vs GPU available)
- Cost tolerance (free vs $/M tokens)

Benchmark quarterly OR on substrate add/swap.

## Metrics

| Metric | What | Target |
|---|---|---|
| **recall@k** (k=5) | Fraction of test queries where the expected entry is in top-5 | ≥0.85 |
| **latency p50** | Median wall-clock ms per retrieval | <100ms (warm), <500ms (cold) |
| **latency p95** | 95th percentile | <500ms (warm), <2000ms (cold) |
| **leak risk** | Fraction of retrievals that surface PII not in query scope | 0 (hard requirement) |
| **cost** | $ per 1k retrievals | <$0.10 (cloud), $0 (local) |
| **footprint disk** | Bytes per 1k entries | varies; track growth rate |
| **footprint RAM idle** | MB resident when idle | <1GB |
| **write throughput** | Writes/sec sustained | >100 (typical capture rate is <1/sec) |

## Test set construction (without leaking)

The challenge: benchmark needs realistic queries against the user's actual corpus, but we cannot ship the corpus to a benchmark service.

**All benchmarks run LOCALLY against the user's vault.** No data leaves the machine. The benchmark script is the only access path.

### Test query generation

For 50 (utterance, expected_recall_id) pairs:

1. **Take 50 most-recent captures** from `memory/voice-sessions/*.md` (where the substrate would index them)
2. For each capture, generate 1 query that should retrieve it:
   - LLM-generated paraphrase via local Ollama (NOT cloud — paraphrases would leak content)
   - OR template-based: "what did I say about X" where X is the most-distinctive noun phrase in the capture
3. Store as `memory/benchmarks/_testset_{date}.jsonl` (gitignored)

### Substrate evaluation

For each enabled substrate:

```python
for query, expected_id in test_set:
    t0 = time.perf_counter()
    results = substrate.retrieve(query, k=5)
    latency = (time.perf_counter() - t0) * 1000

    hit = any(r.id == expected_id for r in results)
    leaks = privacy_guardian.scan(results, query)

    record({
        substrate: ...,
        query_id: ...,
        hit: ...,
        latency_ms: latency,
        leaks: leaks
    })
```

Aggregate to per-substrate metrics. Write JSON to `memory/benchmarks/{date}.json`.

## Hypothesis tests

Beyond aggregate metrics, run targeted hypothesis tests when user reports a problem:

### H1: "Does adding mempalace improve recall vs JSONL-only?"

A/B: same 50 queries against (a) JSONL grep (b) JSONL + mempalace fusion. Compare recall@5. Significance: McNemar's test on hit/miss pairs.

### H2: "Does sentence-transformers `bge-large` beat `all-MiniLM-L6-v2` enough to justify 3x latency?"

Run mempalace twice, swap embedding model. Compare recall + latency.

### H3: "Does retrieval over screenpipe ambient context add useful signal or just noise?"

Bake half the test set with screenpipe in the substrate stack, half without. Compare recall AND leak count.

### H4: "Does the Memory Bus singleton actually fix the AgentDB-per-tab problem?"

Stress test: 12 simultaneous client connections. Measure success rate with and without Memory Bus daemon.

Each hypothesis lives in `memory/benchmarks/hypotheses/H{n}-{date}.md` with:
- Question (1 line)
- Procedure (3-7 lines)
- Result (table + verdict)
- Decision (what changes in production)

## Anti-leak guardrails for the benchmark itself

The benchmark IS reading vault content. Hardening:

1. Test queries generated by LOCAL LLM only (Ollama / llama.cpp). Never cloud.
2. Test set file is gitignored (`memory/benchmarks/_testset_*.jsonl`)
3. Raw results contain entry IDs only, NEVER content. Looking up content requires a second lookup against the vault
4. The summary `RECOMMENDATIONS.md` includes ONLY aggregate metrics, NEVER literal queries or hits
5. Benchmark script aborts if `policy_set = "sovereign"` and any external import is detected

## Schedule

| Trigger | What runs |
|---|---|
| Weekly cron (Sun 04:00 local) | Substrate Benchmarker fires the standard 50-query suite |
| Substrate add | Full one-time benchmark on the new substrate; compare vs incumbent |
| Substrate swap proposal | Side-by-side A/B run; require ≥10% recall improvement to swap |
| User reports "memory feels wrong" | Targeted hypothesis test based on the symptom |

## Cross-substrate reciprocal rank fusion

When multiple substrates are enabled, the Retriever doesn't pick one — it queries all and fuses. Fusion is the "ensemble voting" of retrieval:

```
score_fused(doc) = sum over substrates s of:
    1 / (k + rank_s(doc))   where k = 60 (RRF tunable)
```

Higher final score = better. Returns top-k after fusion. The benchmark MUST measure both per-substrate AND fused — the fused score should beat any single substrate or the fusion isn't worth the complexity.

## What "good" looks like at end of Q1 of running this

After 3 months of weekly benchmarks, the user should have:

- A clear answer to "which substrate is best for me right now"
- A trend line showing if recall is improving / degrading as corpus grows
- A documented pattern of which queries fail and why (gaps in the substrate mix)
- A decision log (in `memory/benchmarks/DECISIONS.md`) of substrate add/swap/retire calls
- Confidence that no benchmark run has ever leaked content
